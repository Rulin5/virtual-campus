# 对话记录 — 小白问答

> 本文件记录了从零开始理解整个项目的完整对话过程，适合对技术不熟悉的同学阅读。

---

## 1. 项目是什么

**问**：这个项目到底在做什么？

**答**：做一个像素 RPG 游戏风格的虚拟校园网站。用户操控一个像素小人在校园地图上走动，走进图书馆按 E 就能看到介绍，和 NPC 对话，接任务、做任务。最终目标是做成一个平台——不需要写代码，管理员在后台网页上填表就能配置整个校园。

---

## 2. 项目分几个阶段

**问**：整个项目怎么分阶段？

**答**：分两大步。

**第一步（01-像素RPG作品集复刻）**：纯前端。先 1:1 模仿一个现成的像素 RPG 作品集网站 peteroravec.com，目的是学会游戏引擎怎么用。这一步不需要服务器，做完就是一个能打开的网页。

**第二步（02-虚拟校园平台搭建）**：加后端。把第一步的游戏内容换成校园内容（教学楼、图书馆），加上登录系统、数据库、后台管理、多人在线。

---

## 3. 整个系统是怎么跑的（三层汉堡结构）

**问**：整个系统是怎么跑起来的？

**答**：就像汉堡分三层：

- **上层（你看到的页面）**：登录页、校园选择、游戏画面、弹窗 — 浏览器打开就能看到
- **中层（游戏引擎）**：控制角色走路、地图滚动、NPC 移动、碰撞检测 — Phaser 3 在浏览器里跑
- **底层（服务器和数据库）**：存用户账号、NPC 对话、任务进度 — Go 程序在后台跑

**完整流程举例**：浏览器 → 加载页面 → 显示登录框 → 输入账号密码 → 服务器验证 → 返回"通过" → 跳转校园选择 → 选校园 → 进入游戏 → 游戏引擎启动 → 小人出现 → 按方向键 → 小人移动 → 走到 NPC 旁按 E → 浏览器请求服务器"这个 NPC 会说什么" → 服务器查数据库 → 返回对话内容 → 弹窗显示

---

## 4. 前端 vs 游戏

**问**：前端和游戏有什么区别？

**答**：它们都在浏览器里跑，但各管各的。

| 前端 | 游戏 |
|------|------|
| 管"网页界面"：登录框、校园列表、按钮、表单 | 管"游戏画面"：地图、小人、NPC、动画 |
| 用 React 做 | 用 Phaser 3 做 |
| 类比：超市的货架和收银台 | 类比：超市里的游乐区 |

---

## 5. 后端 vs 后台

**问**：后端和后台有什么区别？

**答**：完全不是一回事。

| 后端（Backend） | 后台（Admin Panel） |
|-----------------|-------------------|
| 程序自动跑，处理每个用户的请求 | 管理员打开的网页，人在操作 |
| 验证密码、查数据库、返回数据 | 添加 NPC、编辑对话、发布新闻 |
| 类比：餐厅后厨，不停炒菜出菜 | 类比：餐厅经理办公室，决定菜单和价格 |

**举例**：
- 后端做的事（自动）：用户走到 NPC 旁按 E → 收到请求 → 验证 Token → 查数据库 → 返回对话
- 后台做的事（管理员提前做好的）：管理员昨天在后台网页上填了个表——NPC 名称：图书馆老师，对话：欢迎来到图书馆 → 保存到数据库

## 6. 什么是响应式

**问**：什么叫响应式？

**答**：同一个网页，在不同屏幕大小的设备上自动调整布局。

- 电脑上：商品一排 4 个，左侧有分类菜单
- 手机上：商品一排 2 个，菜单折叠成"三横线"按钮

**实现方式**：CSS 里写条件判断——"如果屏幕宽度小于 768 像素，把宽度改成 100%"。一份代码，自动判断设备。

## 7. 为什么要调 API

**问**：为什么要调 API？

**答**：因为浏览器和数据库不能直接对话。数据库就像银行金库，不能让所有人直接进去翻。API 就是银行柜员——告诉柜员你要什么，柜员进去金库操作，然后给你结果。浏览器从头到尾不知道数据库在哪、密码是什么。

---

## 8. 每个数据库都有一个 API 吗

**问**：每个数据库都有一个 API 吗？

**答**：不是。数据库本身只是一个存东西的仓库，只会增删改查。它不会提供 API。API 需要你自己写后端程序来实现。数据库是哑巴仓库，API 是你给它配的翻译官。

---

## 9. 我们的 API vs 调 AI 模型的 API

**问**：我们的 API 和调 ChatGPT 的 API 是一回事吗？

**答**：完全不是。"API"只是"接口"的意思，但调什么完全不一样。

| 我们的 API | 调 AI 模型的 API |
|-----------|-----------------|
| 我们自己写的 Go 程序 | OpenAI/Anthropic 的服务器 |
| 查我们自己的数据库 | 把文字发给 AI，AI 生成回复 |
| 不要钱（自己的服务器） | 按字数收费 |
| 类比：自家门铃 | 类比：打客服电话 |

**我们整个项目从头到尾不需要调用任何 AI 模型的 API。**

## 11. 一个请求的完整旅程

**问**：在游戏里走到 NPC 面前按 E，背后发生了什么？

```
1. 你的手指按 E
2. Phaser 检测到按键 → 检查你离哪个 NPC 最近 → "图书馆老师"
3. 浏览器发请求：GET /api/npcs/library_teacher/dialogue
   自动带上 JWT 通行证
4. Go 服务器收到 → 验证通行证有效 → 查 PostgreSQL：
   "图书馆老师的对话是什么"
5. 数据库返回 JSON：
   {"npcText":"欢迎来到图书馆！","options":[{"text":"想借书"},{"text":"随便看看"}]}
6. Go 服务器返回给浏览器
7. Phaser 收到数据 → 在画面上画对话气泡
8. 你点"想借书" → 重复步骤 3-7
```

整个链条断任何一个环节，功能就崩了。

## 12. 地图是怎么做的

**问**：游戏里的地图是怎么画出来的？

**答**：就像一个拼图。把一张校园地图切成 16×16 像素的小方块（瓦片），每个方块标记为"草地"或"道路"或"建筑"。把所有瓦片按编号拼起来，就是完整的校园地图。

地图太大（2240×2240 像素），一次性渲染会卡死。所以做分块加载——只加载玩家周围 3×3=9 个块，走远的自动删掉。就像手电筒只照亮周围一圈。

## 13. JWT 是什么

**问**：JWT 是什么？

**答**：一张"电子通行证"。你登录之后服务器发给你，之后每次请求都自动带上。服务器看一眼通行证就知道"这个人已经登录了"，不需要每次都输密码。

完整流程：注册（填邮箱密码→存数据库）→登录（验证密码→发 JWT）→后续请求（自动带 JWT→服务器验证→返回数据）。

---

## 14. WebSocket 是什么

**问**：WebSocket 是什么？和 HTTP 有什么区别？

**答**：
- **HTTP**：一问一答，答完就断开。像你打电话问"今天几点关门"，对方回答后挂断。
- **WebSocket**：对讲机，一直保持连接。A 说一句话，B 立刻能听到。

WebSocket 用于：玩家位置同步（A 走一步，B 就看到 A 动了）、地图聊天、实时活动通知。

---

## 15. Docker 是什么

**问**：Docker 是干什么的？

**答**：把整个项目（前端 + 游戏 + 后端 + 数据库 + 缓存 + 存储）打包成一个"集装箱"。部署时一条命令 `docker compose up -d`，全部自动启动。不用手动安装配置每个服务。
