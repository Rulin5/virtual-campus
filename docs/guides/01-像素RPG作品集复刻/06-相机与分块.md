# 第 6 章：相机与分块系统

> **本章目标**：理解相机跟随和分块加载的原理，确保大地图不卡顿。
>
> **预计时间**：1-2 小时

---

## 6.1 为什么需要分块？

地图是 2240×2240 像素（140×140 瓦片 × 24 层 = 470400 个瓦片）。如果全部渲染：
- GPU 需要绘制几十万个矩形 → 帧率掉到个位数
- 内存在 500MB+

**分块思想**：只渲染玩家周围的 3×3 = 9 个块，其余全部丢弃。每次玩家移动到新块时重新加载。

```
完整地图 140×140 瓦片
┌──┬──┬──┬──┬──┬──┬──┐
│  │  │  │  │  │  │  │   每个块 = 20×20 瓦片
├──┼──┼──┼──┼──┼──┼──┤   共 7×7 = 49 个块
│  │  │░░│░░│░░│  │  │
├──┼──┼░░┼░░┼░░┼──┼──┤   只加载 ░░ 区域
│  │  │░░│👤│░░│  │  │   = 玩家周围的 9 个块
├──┼──┼░░┼░░┼░░┼──┼──┤
│  │  │░░│░░│░░│  │  │
└──┴──┴──┴──┴──┴──┴──┘
```

## 6.2 ChunkManager 工作原理

```
1. update(playerX, playerY) 被调用（每帧）
   │
2. 计算玩家在哪个块
   chunkCol = floor(playerX / (20 * 16))
   chunkRow = floor(playerY / (20 * 16))
   │
3. 块没变 → 直接返回（大部分帧都是这样）
   块变了 → 继续
   │
4. 计算可见范围 (minCol ~ maxCol, minRow ~ maxRow)
   │
5. 遍历 activeChunks：
   - 不在可见范围 → destroy() + delete
   │
6. 遍历可见范围：
   - 不在 activeChunks → loadChunk()（创建 Graphics，画瓦片）
```

## 6.3 关键参数调优

```javascript
// chunk-manager.js
new ChunkManager(scene, mapData, mapInfo, chunkSize, visibleRange)

// chunkSize:    每块多少瓦片（推荐 15-25）
//   → 越小：更新越频繁，但每块绘制量少
//   → 越大：每块绘制量大，但切换不频繁

// visibleRange: 保留周围多少圈（推荐 1-2）
//   → 1: 3×3=9 块，内存最省，但边缘容易露出空白
//   → 2: 5×5=25 块，更保险，但内存使用翻倍
```

## 6.4 相机跟随参数

```javascript
this.cameras.main.startFollow(target, roundPixels, lerpX, lerpY);

// roundPixels: true = 像素对齐（推荐像素游戏用 true）
// lerpX, lerpY: 0~1，相机跟随的平滑度
//   → 1.0: 瞬间跟随（生硬）
//   → 0.1: 非常平滑（有惯性感，推荐）
//   → 0.5: 中等平滑
```

## 6.5 性能优化建议

如果地图仍然卡顿：

1. **减少渲染层数**：`maxLayers = Math.min(5, ...)`
2. **减小 visibleRange**：`new ChunkManager(..., 20, 1)`
3. **预渲染 chunk 到 RenderTexture**：一次画好整个 chunk 的纹理，后续直接贴图
4. **使用 Phaser Tilemap** 替代 Graphics.fillRect（GPU 加速）

ChunkManager 的完整代码已在 [第 4 章](04-瓦片地图.md) 中提供。

## 6.6 验证方法

1. 移动角色，地图应该是"流动的"——前面的块出现，后面的块消失
2. F12 → Performance 标签 → 录制几秒 → 查看 FPS（应保持 60）
3. 浏览器任务管理器（Shift+Esc）查看内存（应 < 200MB）
